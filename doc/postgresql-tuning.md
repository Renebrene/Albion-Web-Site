# Оптимизация PostgreSQL: замеры и рекомендации

Дата замеров: **2026-10-19**. Стенд: локальный сервер Albion, PostgreSQL 16.15
(Ubuntu), 12 CPU, 32 ГиБ RAM, NVMe. В кластере две рабочие базы: `albion`
(64 МБ) и `photobase_ingest_test` (22 МБ). Настройки не менялись — документ
фиксирует текущее состояние и обоснованные рекомендации.

## 1. Текущие настройки

| Параметр | Значение | Комментарий |
|---|---:|---|
| `shared_buffers` | 128 МБ | задан в `postgresql.conf` |
| `work_mem` | 4 МБ | на одну сортировку/хэш-операцию |
| `maintenance_work_mem` | 64 МБ | на одну операцию обслуживания |
| `effective_cache_size` | 4 ГиБ | только оценка для планировщика |
| `max_connections` | 100 | задан в `postgresql.conf` |
| `random_page_cost` | 4.0 | значение по умолчанию |
| `effective_io_concurrency` | 1 | значение по умолчанию |
| `shared_preload_libraries` | пусто | `pg_stat_statements` не включён |

## 2. Что реально занимает RAM

- **`shared_buffers` — 128 МБ.** Это общий кэш страниц PostgreSQL. Он один
  на весь кластер и уже вмещает обе рабочие базы (64 + 22 МБ) с запасом.
- **Приватная память backend-процессов — около 84 МБ суммарно.** Замер по
  `statm` для всех процессов `postgres`: примерно 3,6–5,5 МБ на обычное
  соединение плюс отдельные служебные процессы. Это каталоги, планы,
  соединения и т.п.
- **`work_mem` не выделяется постоянно.** 4 МБ — верхняя граница на одну
  сортировку/хэш-операцию. При нескольких одновременных сложных запросах
  расход может умножаться, но при текущих запросах сортировки занимают
  0,5–2 МБ.
- **`maintenance_work_mem` — 64 МБ** только на время `VACUUM`, `CREATE INDEX`
  и подобных операций. Постоянно эта память не занята.
- **`effective_cache_size` — 4 ГиБ — не физический расход.** Это подсказка
  планировщику, сколько данных может держать ОС в page cache. Реально
  `buff/cache` на хосте — около 15 ГиБ.
- **Соединения.** Idle-сессия не держит `work_mem`; основной её расход —
  несколько мегабайт приватной памяти backend-процесса.

Итоговая оценка: PostgreSQL занимает порядка **150–250 МБ** (84 МБ приватной
памяти + разделяемые буферы/библиотеки), а не гигабайты. Основную RAM на
машине потребляют приложение и локальная LLM, а не СУБД.

### Проверка `work_mem`

| `work_mem` | Поведение сортировки | Время |
|---|---|---:|
| 1 МБ | external merge, 1 872 КБ на диск, 235 temp-блоков | 16,3 мс |

| 8 МБ | в памяти, 5 961 КБ | 15,6 мс |

4 МБ — достаточный минимум: при 1 МБ запрос уже уходит на диск, а 8 МБ не
ускоряет его.

### CPU и соединения

| Сценарий | CPU PostgreSQL | Комментарий |
|---|---:|---|
| 50 запросов `/api/home` | 0,09 с (≈7,5% одного ядра) | 0 дисковых чтений, 159 350 buffer hits |
| 10 запросов `/api/constructions` | 0,02 с (≈8,4% одного ядра) | в основном CPU приложения и сериализация |
| 20 запросов `/api/search/v2` | 0,06 с (≈5,9% одного ядра) | поиск идёт по каталогу в памяти |

Под нагрузкой 40 одновременных `/api/home` пик составил **19 соединений**
(7 active, 10 idle, 9 idle in transaction). Это кратковременные транзакции
внутри запросов, не утечка. `max_connections = 20` оказался бы на грани
отказа; 100 — безопасно.

Латентность: `/api/home` — медиана 35 мс последовательно; при 40 параллельных
запросах — 569 мс (очередь на стороне приложения: PostgreSQL в это время
почти не нагружен). `/api/search/v2` — медиана 8 мс, p95 293 мс; вероятная
причина — прогрев каталога в worker-процессах.

## 4. Выводы по предложенным параметрам

| Параметр | Предложение | Фактический вывод |
|---|---|---|
| `shared_buffers` | 25% RAM (≈8 ГБ) | **Не нужно.** Базы вместе 86 МБ, 128 МБ уже покрывают горячие данные; cache hit >99,5%. 8 ГБ отнимут RAM у приложения и Ollama. При желании — 256 МБ. |
| `work_mem` | 8–16 МБ | **Оставить 4 МБ.** Сортировки укладываются в 1,9 МБ, temp-файлов нет. 8 МБ не ускоряет; 16 МБ увеличит худший расход при параллельных запросах. |
| `maintenance_work_mem` | 64–128 МБ | **64 МБ достаточно** для крупнейшей таблицы 34 МБ. 128 МБ — необязательный запас для `VACUUM`/индексов. |
| `effective_cache_size` | 2–4 ГБ | **4 ГБ уже стоит.** Это не расход памяти; менять не обязательно. |
| `max_connections` | 10–20 | **Опасно.** Наблюдался пик 19 соединений; в кластере также работает вторая база. Оставить 100 или снизить до 50–60. 10–20 — только после внедрения пула соединений. |

## 5. Рекомендуемые действия

### Приоритет 1 — наблюдаемость и статистика

1. **`ANALYZE` после импорта уже добавлен** в
   `backend/importer/staging_to_postgres.py`: перед `COMMIT` обновляется
   статистика `construction_imports`, `cities`, `constructions`, `surfaces`,
   `surface_availability` и `construction_media`. Это дешёвая операция
   (1–5 тыс. строк) и делает оценки планировщика предсказуемыми сразу после
   загрузки. Покрыто тестом `backend/tests/test_import_analyze.py`.

2. Включить `pg_stat_statements` и безопасный таймаут транзакций. Готовый
   идемпотентный скрипт: [`../deploy/postgresql-tuning.sh`](../deploy/postgresql-tuning.sh).
   Он также задаёт `maintenance_work_mem = 128 МБ` и
   `effective_cache_size = 8 ГБ` (только подсказка планировщику). Запуск:

   ```bash
   # из корня проекта
   sudo ./deploy/postgresql-tuning.sh
   ```

   Скрипт меняет `shared_preload_libraries`, поэтому перезапускает кластер.
   В кластере есть вторая база — выполняйте в окно обслуживания. Если
   `shared_preload_libraries` уже содержит другие библиотеки, скрипт
   остановится, чтобы не перезаписать их.

3. Проверять `pg_stat_activity` на долгие `idle in transaction`. Скрипт выше
   задаёт `idle_in_transaction_session_timeout = '60s'`; текущая нагрузка
   таких транзакций не создаёт, но настройка защищает от зависших запросов.

### Приоритет 2 — при росте нагрузки

4. **Пул соединений — реализован.** `backend/services/data_service.py`
   использует `psycopg_pool.ConnectionPool`: `min_size=1`,
   `max_size=ALBION_DB_POOL_MAX` (по умолчанию 4) на worker. Отдельное
   соединение для advisory-lock/диагностики — `get_raw_connection()`.
   После этого `max_connections` можно уменьшить до 40–60.

5. **Кэш статистики главной.** `/api/home` считает несколько агрегатов на
   каждый запрос. Если появятся жалобы на latency под нагрузкой, кэшировать
   их на 30–60 секунд с инвалидацией по существующей метке
   `tmp/.data_cache_stamp`.

### Приоритет 3 — только после измерений

6. Для NVMe можно рассмотреть `random_page_cost = 1,5` и
   `effective_io_concurrency = 200`. Но текущие планы полностью в памяти,
   поэтому выигрыш не гарантирован; менять по одному параметру и сравнивать
   `EXPLAIN (ANALYZE, BUFFERS)`.

## 6. Чего не делать

- Не ставить `shared_buffers = 8 ГБ` «по правилу 25%»: это правило для
  выделенного сервера БД с большим рабочим набором. Здесь база целиком 64 МБ.
- Не уменьшать `max_connections` до 10–20 при текущей архитектуре без пула:
  пик уже достигал 19.
- Не поднимать `work_mem` до 16 МБ без temp-файлов: память умножается на
  число одновременных сортировок.
- Не менять несколько параметров сразу: эффект будет невозможно измерить.

## 7. Как повторить замеры

```sql
-- текущие значения
SELECT name, setting, unit, source FROM pg_settings
WHERE name IN ('shared_buffers','work_mem','maintenance_work_mem',
               'effective_cache_size','max_connections');

-- кэш и temp-файлы
SELECT datname, blks_read, blks_hit,
       round(100.0*blks_hit/nullif(blks_hit+blks_read,0),2) AS hit_pct,
       temp_files, temp_bytes
FROM pg_stat_database WHERE datname = current_database();

-- размеры таблиц
SELECT relname, pg_size_pretty(pg_total_relation_size(oid)) AS total
FROM pg_class
WHERE relnamespace = 'public'::regnamespace AND relkind = 'r'
ORDER BY pg_total_relation_size(oid) DESC LIMIT 15;

-- план с буферами
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
```

Для процессорного времени PostgreSQL удобно сравнивать поля `utime`/`stime`
из `/proc/<pid>/stat` до и после нагрузки. Для приватной памяти —
`rss - shared` из `/proc/<pid>/statm`; суммировать `RSS` процессов нельзя,
разделяемые страницы посчитаются многократно.
